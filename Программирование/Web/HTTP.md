**HTTP (Hyper Text Transfer Protocol)** - прикладной протокол передачи данных, изначально предназначенный для гипертекстовых документов. Реализует клиент-серверную архитектуру. Клиент и сервер взаимодействуют, обмениваясь отдельными сообщениями (не потоком данных).

Структура запроса:
```
<Метод> <URI> <Версия протокола>
<Заголовки>
	...
</Заголовки>
CRLF
<Тело запроса>
	...
</Тело запроса>
```

Структура ответа:
```
<Версия протокола> <Статус> <Пояснение>
<Заголовки>
	...
</Заголовки>
CRLF
<Тело ответа>
	...
</Тело ответа>
```

**Замечание**: В запросе и ответе тело запроса может отсутствовать.

## Методы
В HTTP определены следующие методы:
1. **GET**. Извлечение любой информации, идентифицируемой с помощью Request-URI. Если URI запроса относится к процессу создания данных, то в качестве объекта в ответе возвращаются созданные данные.
2. **HEAD**. Извлечение заголовков о сущности в запросе.
3. **POST**. Отправляет данные на сервер для создания или обновления запрашиваемого ресурса. Данные ресурса указываются в теле запроса. Ответы на этот метод не могут кэшироваться, если только в ответе не указаны соответствующие поля заголовка `Cache-Control` или `Expires`. Однако, ответ 303 может указывать на кэшируемый ресурс.
4. **PUT**. Создает новый ресурс или заменяет представление целевого ресурса данными, представленными в теле запроса.
5. **DELETE**. Удаляет указанный ресурс.
6. **OPTIONS**. Используется для описания параметров соединения с целевым ресурсом. Клиент может указать особый URL для обработки метода OPTIONS, или `*` чтобы указать весь сервер целиком.
7. **PATCH**. Частично изменяет ресурс. В отличие от PUT, который полностью заменяет ресурс, PATCH обновляет ресурс.
8. **TRACE**. Выполняет проверку обратной связи по пути к целевому ресурсу, позволяя провести тестирование и отладку.
9. **CONNECT**. Передает данные через прокси-сервер с поддержкой сквозного шифрования между клиентом и ресурсом.

**Замечание**: Не следует использовать GET для отправки конфиденциальных данных, поскольку они будут закодированы в Request-URI.

### Свойства методов

##### Безопасный метод
Метод является **безопасным**, если его семантика по существу доступна только для чтения. Клиент, отправляя безопасный запрос, не ожидает и не запрашивает изменения состояния на сервере. Сервер физически может что-то изменить (логи, счётчики), но клиент в этом не участвует.

##### Идемпотентный метод
Метод является **идемпотентным**, если одинаковые запросы, дают один и тот же эффект, не изменяющий состояние сервера.

##### Кешируемый
Ответ на запрос можно хранить в кеше и использовать повторно. Это зависит не только от метода, но и от заголовков `Cache-Control`, `Vary`, `Expires` и т.д.

**POST** и **PATCH** кэшируемы только при явных заголовках кешируемости (`Cache-Control` + `Content-Location`).

| Метод   | Запрос имеет тело | Успешный ответ имеет тело | Безопасный | Идемпотентный |           Кэшируемый           |
| ------- | :---------------: | :-----------------------: | :--------: | :-----------: | :----------------------------: |
| GET     |        Нет        |            Да             |     Да     |      Да       |               Да               |
| HEAD    |        Нет        |            Нет            |     Да     |      Да       |               Да               |
| POST    |        Да         |            Да             |    Нет     |      Нет      | Нет (только если явно указано) |
| PUT     |        Да         |           Может           |    Нет     |      Да       |              Нет               |
| DELETE  |        Нет        |           Может           |    Нет     |      Да       |              Нет               |
| PATCH   |        Да         |           Может           |    Нет     |      Нет      | Нет (только если явно указано) |
| TRACE   |        Нет        |            Да             |     Да     |      Да       |              Нет               |
| CONNECT |        Нет        |            Нет            |    Нет     |      Нет      |              Нет               |

## MIME типы
**Медиа тип** (**Multipurpose Internet Mail Extensions** или **MIME тип)** - стандарт, который описывает природу и формат документа, файла или набора байтов.

Структура MIME-типа: `тип/подтип`

**Тип** представляет общую категорию, в которой находится тип данных. **Подтип** же строго отождествляется с отдельным типом данных, представляемых данным MIME типом.

Примеры MIME типов:
- `text/plain`: простой текст без форматирования.
- `image/jpeg`: изображение в формате JPEG.
- `multipart/form-data`: данные веб-форм, включая текстовые поля и файлы.
- `application/json`: данные в виды json.

## Заголовки
Заголовки позволяют клиенту и серверу отправлять дополнительную информацию вместе с сообщениями.

Заголовки можно разделить на 4 группы:
1. **Основные (General)**. Используются в запросе и ответе.
2. **Заголовки запроса (Request)**. Используются только в запросах.
3. **Заголовки ответа (Response)**. Используются только в ответах.
4. **Заголовки сущности**. Сопровождают каждую сущность сообщения.

#### Примеры заголовков

**Accept** - указывает, какие типы контента (MIME типы), клиент может понять

**Allow** - список поддерживаемых методов.

**Content-Length** - указывает размер отправленного тела объекта в байтах.

**Content-Type** - используется для определения MIME-типа ресурса.

**Host** - указывает хост и порта сервера, на который отправляется запрос.

**User-Agent** - строка с характеристиками агента пользователя (ОС, производитель, тип приложения и т.д.)

## Статусы

#### Информационные (1XX)
Информирует о процессе передачи. В HTTP/1.0 ответы должны игнорироваться, а в HTTP/1.1 клиент должен быть готов принять этот класс сообщений как ответ, но ничего не отправлять серверу. Сообщения от сервера содержат только стартовую строку ответа и, если требуется, несколько специфичных для ответа заголовков. Прокси-серверы должны отправлять такие сообщения дальше от сервера к клиенту.

Примеры:
`100 Continue` - клиент может продолжить запрос
`102 Processing` - сервер получил и обрабатывает запрос, но ответа пока нет.

#### Успешные (2XX)
Информирует об успешном принятии и обработки запроса клиента.

Примеры:
`200 OK` - запрос успешно выполнен.
`201 Created` - запрос выполнен успешно, в и результате был создан новый ресурс.
`202 Accepted` - запрос был принят на обработку, но еще не завершен.

#### Перенаправление (3XX)
Сообщают клиенту, что для успешного выполнения операций, необходимо сделать другой запрос.

Примеры:
`300 Multiple Choices` - запрос имеет более одного возможного ответа. Пользователь или его агент должен выбрать один из них.
`303 See other` - клиенту необходимо получить запрошенный ресурс по другому URI с помощью GET.

#### Ошибки клиента (4XX)

Примеры:
`400 Bad Request` - сервер обнаружил в запросе клиента синтаксическую ошибку.
`401 Unauthorized` - для доступа к запрашиваемому ресурсу требуется аутентификация.
`403 Forbidden` - сервер понял запрос, но он отказывается его выполнять из-за ограничений в доступе для клиента к указанному ресурсу.
`404 Not Found` - сервер понял запрос, но не нашел соответствующего ресурса по URI.
`405 Method Not Allowed` - указанный клиентом метод нельзя применить к текущему ресурсу.

#### Ошибки сервера (5XX)
Необрабатываемые исключение при выполнении операций на стороне сервера.

Примеры:
`500 Internal Server Error` - любая внутренняя ошибка сервера, которая не входит в рамки остальных ошибок класса.
`501 Not Implemented` - сервер не поддерживает возможностей, необходимых для обработки запроса.
`502 Bad Gateaway` - сервер, выступающий в качестве шлюза, получил недопустимый ответ от целевого сервера.

# Кэширование
Техника кэширования заключается в  сохранении копии полученного ресурса для возврата этой копии в ответ на дальнейшие запросы. Запрос на ресурс, имеющийся в веб-кеше, перехватывается, и вместо обращения к исходному серверу выполняется загрузка копии из кэша.

Кэши делятся на:
1. **Кэши совместного использования (shared)**. Хранятся копии, которые могут направляться различным пользователям.
2. **Приватный кэш**. Предназначен для отдельного пользователя. Хранится в браузере пользователя.

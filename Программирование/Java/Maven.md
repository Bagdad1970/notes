
Apache Maven - это инструмент для сборки Java-проектов. Используя POM, Maven управляет компиляцией, тестированием и документированием проекта.


## POM
Объектная модель проекта (POM) - XML-файл, содержащий информацию о проекте и сведения о конфигурации, используемые для управления проектом. При выполнении цели (goal) Maven ищет POM в текущем каталоге, считывает его, получает необходимую информацию о конфигурации, а затем выполняет цель.

## BOM
BOM (bill of materials) - список артефактов, которые экспортирует проект. Это позволяет управлять версиями зависимостей между внутренними проектами с помощью только одной записи в секции `dependencyManagement`.


## Артефакт
Артефакт - это результат, сгенерированный после сборки проекта Maven. Это может быть, например, jar, war или любой другой исполняемый файл.

Кроме того, артефакты включают в себя пять ключевых элементов:
1. `groupId`  позволяет указать организацию или группу, создавшую проект. Например, `io.github.bagdad`
2. `artifactId` задает название конкретного проекта или модуля. Например, `dakarhelper`.
3. `version` определяет текущую версию проекта Maven.
4. `packaging` указывает тип артефакта, создаваемого проектом. Packaging может быть любой, описывающей любой двоичный программный формат, включая ZIP, WAR и т.д.
5. `classifier` - позволяет отделять несколько артефактов, собранных из одного проекта, но для разных целей.
   Например, есть следующие артефакты:
	- `app-1.0-javadoc.jar` (документация);
	- `app-1.0-linux.jar` (выпуск для linux);
	- `app-1.0-sources.jar` (исходный код).
	Каждый из них собран для различных целей.


## Архетип
Архетип — это шаблон проекта, со структурой и заготовками исходных и конфигурационных файлов. Существует множество архетипов, например:
- `maven-archetype-simple` - простой maven проект
- `maven-archetype-webapp` - простой webapp maven проект
- `maven-archetype-plugin` - образец maven плагина

Пример команды создания проекта с помощью архетипа:
```bash
mvn archetype:generate \
	-DarchetypeGroupId=io.github.bagdad \
	-DarchetypeArtifactId=maven-archetype-simple \
	-DgroupId=io.github.bagdad
	-DartifactId=dakarhelper
```


## Фазы и цели
### Фаза
Фаза представляет этап жизненного цикла сборки Maven. Каждая фаза отвечает за выполнение определенной задачи. Причем при запуске фазы сначала выполняются все предыдущие, например, перед фазой `test` будут выполнены фазы `validate` и `compile`.

Основные фазы:
1. `validate` - проверяет правильность проекта и наличие всей необходимой информации для сборки.
2. `compile` - компилирует исходный код проекта.
3. `test` - тестирует скомпилированный исходный код с помощью определенного фреймворка тестирования. Тесты не должны требовать, чтобы код был упакован или развернут.
4. `package` - упаковывает скомпилированный код в распространяемый формат, например в JAR.
5. `verify` - выполняет проверку результатов интеграционных тестов
6. `install` - устанавливает пакет в локальный репозиторий для использования в качестве зависимости для других проектов.
7. `deploy` - выполняется в среде сборки, а также копирует итоговый пакет в удаленный репозиторий.

### Цель
Каждая фаза представляет собой последовательность целей, и каждая цель отвечает за выполнение определенной задачи. При запуске фазы, выполняются все цели, связанные с этой фазой.

Указание цели выглядит как `plugin-prefix:goal

Примеры целей:
`compiler:compile` – компилирует исходный код
`compiler:testCompile` - компилирует исходный код тестов
`install:install` - устанававливает основной артефакта проекта, его POM и подключенные артефакты (исходные тексты, javadoc и т.д.)
`jar:jar` - создайте jar-файл проекта, включая ресурсы


## Зависимости
Зависимости бывают двух типов:
- **Прямые**. Зависимости, указанные явно в pom.
- **Транзитивные**. Зависимости, которые нужны самим прямым зависимостям. При разрешении конфликта версий используется принцип «ближайшей» зависимости, то есть выбирается зависимость, путь к которой через список зависимых проектов является наиболее коротким.

Можно исключить транзитивную зависимость указав ее в блоке `exclusions`.
Пример исключения транзитивной зависимости:
```xml
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-core</artifactId>
    <version>5.3.20</version>
    <exclusions>
        <exclusion>
            <groupId>commons-logging</groupId>
            <artifactId>commons-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```


### Области действия зависимостей
Область действия определяет в какой момент работы приложения доступна зависимость - только во время компиляции, во время тестирования и т.д.
Области действия позволяют ограничить транзитивность зависимостей. Они также изменяют classpath для различных задач сборки.

Область действия зависимостей используется для ограничения транзитивных зависимостей и указания, когда зависимость включается в classpath.

Области действия:
- **Compile**. (По умолчанию) Зависимость доступна на всех этапах работы приложения
- **Provided**. Используется для компиляции или тестирования, но не попадает в финальный артефакт, т.е. будет добавлено в classpath для компиляции и тестирования, но не для выполнения. Не передается транзитивно.
  Пример: Servlet Api - поскольку Tomcat уже предоставляет Servlet Api, отдельная зависимость не нужна в артефакте, но нужна при разработке.
- **Runtime**. Используется только во время выполнения. Для компиляции не используется. Пример: Jdbc driver.
- **Test**. Используется только для тестов, но не при обычном запуске. Пример: JUnit
- **System**. (устарело и не рекомендуется к использованию) Зависимость требуется для компиляции и выполнения. Однако Maven не будет загружать зависимость из репозиториев. Вместо этого будет искать jar в локальной файловой системе по указанному пути.
- **Import**. (доступно только для зависимости типа pom) позволяет определить в одном файле pom в `dependencyManagement` некоторые зависимости с версиями, scope и т.д., а в другом pom (проекте) указать только эти зависимости и ничего более (без версий, scope и т.д.)


## Получение зависимостей
Репозиторий в Maven - это директория, где хранятся все JAR, библиотеки, плагины и любые артефакты, которые Maven может использовать.

Репозитории делятся на:
- **локальные (local)**
- **центральные (central)**
- **удалённые (remote)**

#### Локальный репозиторий
Хранится локально на компьютере. Директория создаётся в момент первого выполнения любой команды Maven.

Хранит все зависимости проекта (библиотеки, плагины и т.д.). Когда выполняется сборка проекта, то все зависимости (их JAR-файлы) автоматически загружаются в локальный репозиторий.

По умолчанию хранит зависимости и конфигурацию в `~/.m2/`

#### Центральный репозиторий
Центральный репозиторий Maven – это репозиториий, который обеспечивается сообществом Maven. Он содержит огромное количество часто используемых библиотек.

Если Maven не может найти зависимости в локальном репозитории, то он автоматически пытается найти их в центральном.

#### Удаленный репозиторий
Maven может не найти необходимые зависимости в центральном репозитории. В этом случае, процесс сборки прерывается и в консоль выводится сообщение об ошибке.

Для предотвращения этой ситуации, можно указать удалённый репозиторий, который определяется разработчиком.

Пример указания удаленного репозитория:
```xml
<repositories>
	<repository>
		 <id>bagdad.lib</id>
		 <url>http://download.bagdad.net/maven2/lib</url>
	</repository>
</repositories>
```

### Процесс поиска зависимостей
При сборке проекта автоматически начинается поиск необходимых зависимостей в следующем порядке:
1. Поиск зависимостей в локальном репозитории.
2. Если не все зависимости удовлетворены, происходит поиск в центральном репозитории. Если они не обнаружены и удалённый репозиторий определён, то происходит переход к шагу 4.
3. Если не все зависимости обнаружены, но удаленный репозиторий не указан, то процесс сборки прекращается и выводится сообщение об ошибке. Иначе - происходит их загрузка в локальный репозиторий из удаленного.


## Плагины maven
По своей сути Maven является фреймворком для исполнения плагинов.

Плагины определяются внутри блока `<plugins>...</plugins>`.
Может иметь несколько целей. Также можно определить фазу, с которой начинается выполнение плагина.

Плагины делятся на:
1. Плагины сборки (**build plugins**). Запускаются во время сборки и должны быть настроены в элементе <build/> из POM.
2. Плагины создания отчетов (**Reporting plugins**). Запускаются во время создания сайта, и настраиваются в элементе <reporting/> из POM. Поскольку результат работы этих плагинов является частью созданного сайта, они должны быть как интернационализированы, так и локализированы.

Примеры плагинов:
- `clean` - очистка окружения после сборки
- `compiler` - компилирует исходный код проекта
- `surefire` - запускает тесты JUnit и создаёт отчёты о тестировании
- `jar` - собирает JAR файл текущего проекта
- `javadoc` - генерирует Javadoc проекта


## Synchronized
Ключевое слово **synchronized** может быть применено к методу или блоку кода.

Каждый объект в Java имеет [[Примитивы синхронизации#Монитор|монитор]], который используется для синхронизации доступа к критической секции.

Когда поток вызывает синхронизированный метод или входит в синхронизированный блок, метод / блок блокируется. Блокировка снимается, когда метод или блок завершается или генерируется исключение.

#### Метод
`synchronized` можно применять к статическому методу и методу объекта.

Пример синхронизации метода:
```java
@Getter  
class Counter {  
    private int count = 0;
    
    public synchronized void increment() {  
        this.count++;
    }  
}  
  
class Executor implements Runnable {  

    private Counter counter;  
    
    public Executor(Counter counter) {  
        this.counter = counter;  
    }  
    
    @Override  
    public void run() {  
        for (int i=0; i<1000; i++) {  
            counter.increment();  
        }  
    }  
}
```

#### Блок
Вместо того, чтобы синхронизировать целый метод, можно синхронизировать только блок кода.

Синтаксис:
```java
synchronized (obj) {
	// код, использующий критическую секцию
}
```

Передаваемый объект `obj` является объектом-монитором. Код блока синхронизируется с объектом-монитором т.е. внутри этого блока кода может выполняться только один поток для каждого объекта monitor.
Если метод статический, то в качестве объекта передается имя класса, и класс будет монитором для синхронизации блока

**Замечание**: В качестве объекта-монитора не может использоваться примитивный тип.

Пример синхронизации блока:
```java
@Getter  
class Counter {  
    private int count = 0;
    
    public void increment() {  
        synchronized (this) {  
            this.count++;  
        }  
    }  
}  
  
class Executor implements Runnable {  
    private Counter counter;  
    
    public Executor(Counter counter) {  
        this.counter = counter;  
    }  
    
    @Override  
    public void run() {  
        for (int i=0; i<1000; i++) {  
            counter.increment();  
        }  
    }  
}
```

## Volatile
Когда процессор выполняет код, он считывает данные не только из основной памяти, но и из кэшей разного уровня (L1, L2 и L3). Использование этих кэшей создает проблему видимости изменений.

Поскольку в современном компьютере может быть несколько процессоров, то мы не можем гарантировать, в каком ядре в конечном итоге будет выполняться поток. Например, вышеупомянутые два потока могут выполняться в двух разных процессорах. В этом случае возникает проблема видимости, когда один процессор использует значение из своего кэша, несмотря на то, что другой процессор уже изменил эту переменную.

Когда поток изменяет значение переменной, он сначала может изменить его в своем локальном кэше. Другие потоки могут не увидеть это изменение немедленно, так как они могут читать устаревшее значение из основной памяти или из своих кэшей.

При выполнении потоки могут кэшировать значения переменных, а компилятор и процессор переупорядочивать инструкции для оптимизации.
**volatile** используется для **неблокирующей** синхронизации доступа к полю экземпляра. При объявлении поля с ключевым словом **volatile**, компилятор и JVM учитывают, что поле может одновременно обновляться другим потоком. При компиляции компилятор вставит соответствующий код, чтобы гарантировать, что изменение **volatile** переменной в одном потоке будет видны из основной памяти, а не только из кэша конкретного процессора.

**Замечание**: Ключевое слово volatile применимо только к полю класса т.к. значение обычной переменной не разделяется между потоками.

Рассмотрим пример:
```java
class Worker implements Runnable {
    private boolean running = true;
    
    @Override
    public void run() {
        System.out.println("Поток А: Начинаю работу...");
        while (running) {
            // JIT-компилятор с высокой вероятностью "закэширует" переменную running в регистре процессора, так как она не меняется внутри цикла.
        }
        // Эта строка может никогда не выполниться
        System.out.println("Поток А: Работа остановлена.");
    }
 
    public void stop() {
        this.running = false;
    }
}

public class Program {
    public static void main(String[] args) throws InterruptedException{
        Worker worker = new Worker();
        
        Thread workerThread = new Thread(worker);
        workerThread.start();
        
        Thread.sleep(1000);
        
        worker.stop(); // метод вызывается главным потоком
        
        // Ждем завершения "Потока А"
        // Если running не volatile, join() может ждать вечно!
        workerThread.join(2000); // Ждем до 2 секунд
 
        if (workerThread.isAlive()) {
            System.out.println("РЕЗУЛЬТАТ: Поток А все еще работает!");
            System.out.println("Поток А не увидел изменение running = false.");
            System.exit(1); // Завершаем программу, так как поток завис
        }
        else {
            System.out.println("РЕЗУЛЬТАТ: Поток А  успешно завершился.");
        }
    }
}
```

Для корректного выполнения в несколько потоков необходимо объявить переменную `running` как `volatile`.

**volatile** предоставляет две гарантии:
1. **Гарантия Видимости (Visibility)**. JVM никогда не кэшировать эту переменную на уровне потока. Тогда запись в `volatile`-переменную всегда производится в основную память, а чтение `volatile`-переменной всегда происходит напрямую из основной памяти, игнорируя любое кэшированное значение.
2. **Гарантия Упорядочивания (Happens-Before)**. `volatile` устанавливает отношение happens-before, которое гарантирует следующее:
    - запись в `volatile`-переменную происходит **после** всех предыдущих чтений и записей в коде.
    - чтение `volatile`-переменной происходит **до** (happens-before) всех последующих чтений и записей.
    
    Это означает, что `volatile` действует как "барьер памяти". Все, что было до записи в `volatile`-переменную, гарантированно будет видно любому потоку, который **после** записи обратился к `volatile`-переменной.

`volatile` применяется, когда надо обеспечить видимость изменений переменных между потоками. Однако его следует использовать только тогда, когда выполняются оба следующих условия:
- Изменения переменной не зависят от ее текущего значения (т.е. не выполняется `counter++` или `x = x + 1`).
- Запись в переменную производит только один поток, а ее значение считывают один или несколько других потоков.

### Happens-before
Happens-before - это понятие из JMM, которое описывает отношение между операциями чтения и записи в разделяемых переменных. Happens-before обеспечивает определенные гарантии относительно порядка выполнения операций в разных потоках.

Предотвращает определенные типы переупорядочивания инструкций, которые могут производить компиляторы и процессоры для повышения производительности.

**Главное правило happens-before**: Пусть запись в разделяемую переменную происходит до (happens-before) чтения этой переменной. Тогда любое значение, записанное в эту переменную до операции записи, должно быть видимым при операции чтения.

Операции, которые создают happens-before:
1. **Завершение конструктора объекта**. Когда объект инициализируется в одном потоке, и его ссылка становится видимой в другом потоке после завершения конструктора, “happens-before” создается.
2. **Завершение вызова `Thread.start()`**. Когда поток запускается с использованием метода `start()`, он не начинает выполнение кода до завершения этого метода, что создает "happens-before".
3. **Завершение вызова `Thread.join()`**. Когда поток вызывает метод `join()` для другого потока, он блокируется до тех пор, пока другой поток не завершит выполнение, что также создает "happens-before".

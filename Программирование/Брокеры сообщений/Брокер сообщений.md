**Брокер сообщений** — это программа, которая управляет обменом сообщениями между приложениями, сервисами или системами. Причем обмен является асинхронным т.е. один сервис не будет ждать, пока другой обработает его сообщение.

Брокер можно представить как центральный узел. Он получает сообщения от приложений-отправителей и направляет их приложениям-получателям, преобразуя из одного протокола в другой.

![[Pasted image 20260420192510.png]]

Функции брокера:
- **Валидация**. Проверяет формат и содержание сообщений перед их передачей.
- **Маршрутизация**. Определяет место назначения для каждого сообщения.
- **Хранение**. Может временно хранить сообщения, если получатель недоступен, чтобы доставить их позже.
- **Доставка**

Терминология:
**Сообщение** - данные, которые необходимо отправить между приложениями.

**Продюсер** - приложение-источник, которое отправляет сообщения.

**Потребитель** - приложение, которому необходимо принять сообщения.



Получив сообщение от продюсера, брокер добавляет его во внутреннюю очередь. Там оно хранится до тех пор, пока не будет использовано соответствующим потребителем. При этом модели распространения сообщений могут быть разными.

### Точка-точка (Point-to-Point)
Модель используется, когда продюсеры имеют отношения «один-на-один» с потребителями. То есть сообщение должно быть обработано только один раз и только одним получателем.

![[Pasted image 20260420195926.png|616]]



### Публикация-подписка (Publish / Subscribe)
Используется, когда продюсеры имеют отношения «один-ко-многим» с потребителями. Один или несколько продюсеров могут публиковать сообщения по определенной теме, а заинтересованные потребители могут подписаться на нее, чтобы получать эти данные.

### Модель доставки сообщений
#### Push модель
Брокер сам решает, когда и сколько данных отправить потребителю.

#### Pull модель
Продюсеры отправляют данные в брокер, а потом потребители получают данные оттуда.

Отличия моделей:
- **Защита от перегрузки**. Необходимо настроить получение потребителем пакетов данных, а не единичных записей. В Push модели либо пакет отправляется  немедленно, либо накапливается много данных, которые отправляются позже, но потребитель может быть не в состоянии их обработать. Если же настраивать такую систему на низкую задержку, это приведёт к отправке по одному сообщению за раз, но передача всё равно будет буферизирована, что неэффективно. Pull модель решает эту проблему, поскольку потребитель всегда извлекает то количество сообщений, на которое он настроен.

- **Активное ожидание данных**. При использовании Pull модели, если у брокера нет данных, потребитель будет постоянно опрашивать брокер на поступившие данные.

**Индекс** - структура данных, ускоряющая процесс поиска данных в таблице и сортировки. Без индекса СУБД будет просматривать каждую строку для поиска необходимой информации.

Команда (сокращенная) для создания индекса (Postgresql):
```sql
CREATE INDEX название_индекса ON [USING тип_индекса] схема.таблица (столбец1, ..., столбец_n);
```
По умолчанию используется B-дерево.

### Типы индексов
Индексы делятся на:
- **Первичные** - это уникальные индексы в таблице, которые всегда должны иметь какое-то значение и не могут быть равны null. 
- **Вторичные индексы**. Вторичные индексы — это прочие индексы таблицы, которые могут и не быть уникальными.
- **Составные (сцепленные) индексы**. Содержат два или более столбца из одной и той же таблицы. Особенно полезны для обеспечения уникальности сочетания столбцов таблицы в тех случаях, когда нет уникального столбца, однозначно идентифицирующего строку. Составные индексы полезны при выполнение запросов с указанием нескольких полей. Причем порядок перечисление столбцов при создании индексов **учитывается**.

## Представление в БД
Индекс физически представляет отдельный файл, который лежит вместе или рядом с файлом данных таблицы. Рядом потому, что мы можем создать отдельное табличное пространство для хранения индекса. При создании индекса, база данных фиксирует его в своих метаданных.

Метаданные индекса содержат:
- **OID (Object id)** - внутренний идентификатор, который характеризует объект индекса внутри метаданных PostgreSQL. 
- **Relation name** - имя объекта.
- **Schema** - схема, где определён объект индекса.
- **Object owner** - под каким пользователем был создан объект.
- **Tablespace** - табличное пространство, где определён индекс.
- **Amount pages** - количество страниц.
- **Amount tuples** - количество записей. 
- **TOAST таблицы**
- **Type** - тип индекса, у нас он постоянный. 
- **File path** - путь, где лежит файл, который определяет структуру индекса. 
- **Relation size** - общий размер, который мы можем прочитать через функцию  pg_relation_size. Каждая из страниц по правилам PostgreSQL весит 8 килобайт.

## Типы индексов в Postgresql

### B-дерево
Используется для порядковых типов данных, значения которых можно сравнивать и сортировать. Индексируемые данные сохраняются в отсортированном порядке.

![[Pasted image 20260412002408.png|669]]
У нас имеется поддерево слева и поддерево справа от корня дерева. Левое поддерево содержит значения, которые всегда строго меньше корня, а правое поддерево — значения большие или равные корню. Это свойство выполняется и для корня, и для любого внутреннего узла дерева.

B-деревья обладают важными свойствами:
- Они сбалансированы, то есть все листья находятся на одной глубине. Поэтому поиск любого значения занимает одинаковое время.
- Они сильно ветвисты, то есть каждый узел содержит много элементов, часто сотни. За счет этого глубина B-деревьев получается небольшой даже для очень больших таблиц.
- Данные в индексе упорядочены по возрастанию (или по убыванию) как между узлами, так и внутри каждого узла. Узлы одного уровня связаны между собой двунаправленным списком, поэтому можно получить упорядоченный набор данных, просто пройдя по списку в одну или в другую сторону, не повторяя каждый раз путь от корня.

### Хэш-индекс
При создании применяется хэш-функция каждому значению индексируемого столбца. Результат хэширования определяет в какой bucket попадет запись

Bucket назначается по формуле: `bucket_num = hash_val % num_buckets`

Используется для запросов на точное совпадение

Если в БД не найдена запись с использованием хэш-индекса, то выполняется полное сканирование таблицы.

## Рекомендации
1. Избегайте создания индексов для сравнительно небольших таблиц. Для таких таблиц больше подходит полное сканирование. В случае маленьких таблиц нет необходимости в хранении данных и таблиц, и индексов.
2. Индексируйте столбцы, участвующие в многотабличных операциях соединения.
3. Индексируйте столбцы, которые часто используются в конструкциях _WHERE_.
4. Индексируйте столбцы, участвующие в операциях _ORDER_ _BY_ и _GROUP BY_ или других операциях, таких как _UNION_ и _DISTINCT_, включающих сортировку. Поскольку индексы уже отсортированы, объем работы по выполнению необходимой сортировки данных для упомянутых операций будет существенно сокращен.
5. Лучше не индексировать столбцы, состоящие из длинно-символьных строк
6. Столбцы, которые часто обновляются, в идеале не должны быть индексированы из-за связанных с этим накладных расходов.
7. Индексируйте только те таблицы, в которых мало строк имеют одинаковые значения.
8. Сохраняйте количество индексов небольшим.
9. Составные индексы могут понадобиться там, где одностолбцовые значения сами по себе не уникальны. В составных индексах первым столбцом ключа должен быть столбец с максимальной селективностью.
